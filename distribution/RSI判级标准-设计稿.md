# 递归自我改进（RSI）的判级标准 · 设计稿

> 依据：用户提供的 RSI 定义 + DeepRSI 的「可测量」思想
> 目的：**把 RSI 落成可测量、可验证的判据，而不是一段描述**
> 设计时间：R93

---

## 一、先把两个概念分清（用户原文）

| | AI 辅助研发 | 递归自我改进（RSI） |
|:---|:---|:---|
| **谁定目标** | 人类 | 系统参与 |
| **谁做决策** | 人类 | 系统参与 |
| **改进对象** | 产物（代码/论文/实验） | **自身的算法、训练方法、工具链、后续研发流程** |
| **判据** | 产出可用 | **改进必须提高下一轮研发的效率或能力** |

**关键区别一句话**：
> AI 辅助研发是"帮人做事"；RSI 是"改进自己做事的方式，并且下一轮真的更好"。

---

## 二、RSI 的六个层级（本文档的核心）

按用户给的门槛，我把它拆成 **L0–L5**，每一级都有**可验证判据**：

| 级别 | 名称 | 定义 | 可验证判据 |
|:---|:---|:---|:---|
| **L0** | 纯人工 | 无 AI 参与 | — |
| **L1** | AI 辅助 | 模型执行任务，人类控目标/决策/流程 | 有产出；但改进**不持久**（下次从零开始） |
| **L2** | 产物自改进 | 改进被**持久化**，且**下一轮真的用上** | ① 改进写进文件（教训/工具/判据）<br>② 下一轮**自动执行**它（门禁/检查器）<br>③ 产出**可复现**（同一输入同一结果） |
| **L3** | 流程自改进（元层） | 改进的是「**改进的方法**」本身 | ① 新增机制里**「防止再犯类」占比 ≥ 50%**<br>② 机制数量**单调不减**（棘轮）<br>③ 每条机制都有**负控**（证明它真能抓到） |
| **L4** | 跨任务迁移 | 改进能迁移到**它没见过的任务/领域** | ① 有**跨领域引用**记录（A 域的教训在 B 域抓到问题）<br>② 迁移率 ≥ 阈值<br>③ 新任务上手时间**不增长** |
| **L5** | 自模型改进 | 改进**自身基础模型**（权重/架构/训练） | 需要能改自己的权重 —— **本项目做不到，必须如实声明** |

---

## 三、为什么 L4 是真正的分水岭（用户原话的落地）

> 「模型优化一个现有程序，不等于它已经优化了自身的基础模型；
>  模型提高某项任务的分数，也不等于它能够自动提升下一代模型的综合能力。
>  **只有当改进能够可靠地迁移到后续研发任务，并持续提升研发系统本身的能力，
>  才更接近严格意义上的递归自我改进。**」

**翻译成可测的东西**：

```
L2 的问题：我修好了这个 bug —— 但下一个不同的 bug 会不会再犯？
L3 的问题：我加了一条判据 —— 但判据本身有效吗？（要负控）
L4 的问题：这条教训，在【它没想到的场景】里有没有救过我？
```

**所以 L4 的判据必须是「跨领域救场记录」**，而不是"教训数量多"。

## 四、我们项目的真实数据（先摸个底）

```
教训        60 条
PDCA        84 轮
门禁        29 项
负控测试    4 个文件
含「防止再犯类机制」的轮次   31 / 84（37%）
```

**初步判断**：我们大概在 **L2 末期 → L3 初期**。
- ✅ 有持久化（60 条教训写进文件）
- ✅ 有自动执行（29 项门禁每次跑）
- ⚠️ 元层改进占比只有 37%（L3 要求 ≥50%）
- ⚠️ **迁移率没有测量过** —— 这是最缺的一块

## 五、要建的东西

### `tools/rsi_level.mjs` —— RSI 判级器

```
测什么：
  ① 持久化率     改进写进文件的比例
  ② 应用率       下一轮自动执行的比例
  ③ 元层改进占比  「防止再犯类」/ 总改进
  ④ 棘轮单调性    机制数量是否只增不减
  ⑤ 负控覆盖率    有多少机制带负控（证明有效）
  ⑥ 迁移率  ★    教训在【非起源领域】抓到问题的比例
  ⑦ 效率趋势      同样工作量的耗时/轮次是否下降

判什么：
  当前处于 L0–L5 的哪一级（按最低的未达标项卡住）

说什么：
  · 诚实声明天花板（L5 做不到，因为不能改自己权重）
  · 指出升到下一级最小的那一步
```

### 关键设计：迁移率怎么测

```
每条教训有两个字段：
  area   —— 它归属的领域（验证/数据/构建/AI收录/工程…）
  origin —— 它是从哪个具体事故来的

迁移 = 这条教训在【与 origin 不同的场景】里被触发/救场。

我们已经有 84 轮 PDCA 的 act 文本 ——
可以扫：某条教训的 id 在【它诞生那轮之后】的轮次里被提到，
且那些轮次的领域与它的 area 不同 → 算一次迁移。
```

**这是可实现的**，而且正是 DeepRSI 的思路：**用实际任务表现衡量，不听模型自述**。

## 六、写进规则的方式

按本项目纪律「教训要编成可执行判据」：

```
① 新教训 L-60：RSI 必须分级可测，且必须如实声明天花板
   —— 判据：真跑 rsi_level.mjs，且报告里有 level + 天花板声明
② 新门禁 G7：RSI 判级（作为 L2 门禁的一项）
③ 接进云端工作流（每 2 小时测一次，看级别有没有掉）
④ 棘轮：已达成级别只能升不能降（掉级立即红叉）
```

---

## 七、必须写清的「做不到」（这是诚实的一部分）

```
❌ 我们改不了自己的基础模型（权重/架构/训练方法）
   → 所以严格意义的 L5 永远达不到
   → 必须在报告里明确写"天花板 = L4"

❌ 我们改不了"下一代的自己"
   → 每轮对话的模型是固定的
   → 但我们能改【下一轮对话时的工具、判据、上下文】
   → 这才是我们能做到的"自我改进"

★ 诚实的定位：
   本项目是「工具链层面的 RSI」（改进工具 → 下一轮更好用），
   不是「模型层面的 RSI」（改进权重 → 更强的自己）。
   两者都必须说清楚，不能混为一谈。
```

---

## 八、判级逻辑（防自吹）

```
LEVEL = 满足条件的最高级，但【被最低的未达标项卡住】

意味着：
  即使 ⑥ 迁移率很高，
  只要 ③ 元层改进占比 < 50%，
  就卡在 L2 —— 不许跳级。

这是防"自吹已经 L4"的机械保障。
```
