### ② 「Harness = 给它一个框架、一个约束」→ 我们的门禁就是 Harness

演讲原话：

> Harness 本身是什么意思？就是给它一个框架、一个约束。
> 把操控、数据、权限都框起来，让 Agent 在一个有约束的环境中为你服务，
> **这样反而能发挥更大的实力。**

**这和我们做门禁的逻辑完全一致** ——
不是"限制 Agent"，而是**"让 Agent 的输出可被信任，于是可以放手用"**。

**可编程条目**：
```
✅ 已有：L1 护栏 18 条 / L2 门禁 29 项 / L3 自迭代 / 57 条教训
🔲 待补：把「约束清单」显式输出成一个文件，
        让外部（GitHub Actions / 其他 Agent）能读到我们的边界在哪。
        —— 这就是「可交接的 Harness」
```

### ③ 「上下文属于用户」→ 与我们的数据纪律同源

**对照我们的硬规矩**：

② 每个结论带来源

④ 承认边界
⑤ 不信任自我报告

**这是同一种东西**：都是在说**"不要把不属于你的东西据为己有/伪造"**。

## 三、三条「反着用」的启发（演讲没讲，但对我们重要）

### 反 1：云端不是万能 —— 演讲也承认「封闭生态需要 RPA/APA」

演讲：

> 今天的世界更多还是封闭的生态，这就需要另外的能力……
> 这是一个非常不容易做好的能力。

**对我们的意义**：**别指望云端能替我们上传网站、发 npm、发 PR** ——
那些都需要凭据/网页操作，属于"封闭生态"。

**所以我们一直区分**：
```
云端能做的  → 跑验证、报警、写报告（已做）
人必须做的  → 上传、认证、发版、业务判断（已列清单）
```

**这条我们已经做对了**（《云端继续说明.md》里明确写了"做不到什么"）。

---

### 反 2：「上下文」不是越多越好 —— 我们的教训是"扫全仓 130 处，只改 22 处"

演讲强调采集，但**我们的实测教训**是：

```
全仓 130 处过时数字，真正该改的只有 22 文件 35 处：
  · 构建产物     → 重新生成（21 文件 47 处）
  · 历史记录     → 绝不动（3 文件 8 处）
  · 元引用脚本   → 绝不动（5 文件 22 处）
  · 证据行       → 绝不动（35 行）
```

**采集容易，判断"哪些该动"才是难点。**

**可编程条目**：
```
✅ 已有：行级判别 + 三类文件三种处置
🔲 待补：把这条经验抽象成通用规则 ——
        「批量修改前先分类：该改的/该生成的/不该动的」
        写进 lessons，让以后任何批量操作都先做这个分类。
```

---

### 反 3：「让 Agent 不下班」有个前提 —— 它得知道该干什么

演讲的解法是"给它工位"。
但**工位 ≠ 目标**。一个 24 小时运行的 Agent，
如果不知道自己该干什么，只会 24 小时空转。

**我们的解法**（已成体系）：
```
《今晚工作方案.md》  → 今晚该干什么（优先级排序）
《开机后从这里继续.md》→ 开机第一眼
生存法则检查器       → 检查"有没有在动"
今晚工作方案         → 检查"动得对不对"
```

**可编程条目**：
```
✅ 已有：方案文档 + 生存法则
🔲 待补：把「今晚工作方案」的完成度纳入判据 ——
        每轮 PDCA 结束时检查：上一轮定的目标完成了多少？
        完成率 < 50% 时要说明原因（不是默默换目标）。
```
