# 阿里云函数计算 FC 备选方案（云端自续跑）

> 生成时间：2026-10-09
> 定位：**备选方案**。首选是 GitHub Actions（已配置好，见 `.github/workflows/nightly-self-iteration.yml`）。
> 本文准备材料供用户决策，**不代为执行**（需要阿里云账号登录与授权）。

---

## 一、什么时候该用 FC 而不是 GitHub Actions

| 场景 | 用哪个 | 原因 |
|:---|:---|:---|
| 只是想定时跑门禁、累积证据 | **GitHub Actions**（首选） | 零配置、公开仓库免费不限量、结果自动 commit 回仓库 |
| 想让任务离 mackorn.cn 更近 | **阿里云 FC** | 同账号同生态，内网调用快 |
| 国内网络访问不稳定时 | **阿里云 FC** | 不依赖 GitHub 连通性 |
| 需要访问 mackorn.cn 的内网资源 | **阿里云 FC** | 与 ECS/OSS 同 VPC |
| 想把结果直接写进 OSS 或调线上接口 | **阿里云 FC** | 同账号 RAM 授权即可 |

**结论**：先用 GitHub Actions。**只有当你发现 GitHub 经常连不上、或需要内网访问时才切 FC。**

## 二、FC 方案要点（供你决策用）

### 2.1 基本形态

```
运行时：Node.js 20
入口：执行 tools/self_iterate.mjs + tools/enforce_lessons.mjs
触发器：定时触发器（cron）
超时：建议 300 秒（单轮自迭代实测 < 1 秒，门禁 < 3 秒，留足余量）
内存：512 MB 足够（自迭代峰值内存很低）
```

### 2.2 定时触发器 cron 表达式（FC 用 UTC）

```
# 每 2 小时一轮，覆盖北京 20:00 – 次日 14:00
0 0 12,14,16,18,20,22,0,2,4,6 * * *

# 字段：秒 分 时 日 月 周
```

### 2.3 代码怎么进去

FC 不能直接 `git clone`（除非配 Git 触发器）。三种方式：

| 方式 | 做法 | 适合 |
|:---|:---|:---|
| **A. 打包上传** | 把仓库压成 zip，`console` 上传或 `fun deploy` | 一次性、简单 |
| **B. OSS 中转** | 代码包放 OSS，FC 从 OSS 拉 | 版本较多时 |
| **C. CI 自动部署** | GitHub Actions 里加一步，用 `aliyun` CLI 把包推到 FC | 想全自动 |

**推荐 A 起步**：先把流程跑通，再考虑 C。

### 2.4 结果怎么回来

FC 是无状态的，跑完就没了。三种落地：

| 目标 | 做法 |
|:---|:---|
| 写回仓库 | 函数里用 GitHub API 提交（需 PAT，**又一个凭据要管**） |
| 写 OSS | 函数里用 `aliyun-sdk-oss` 上传 JSON 结果 |
| 写回 mackorn.cn | 加一个受 token 保护的接收端点，函数 POST 过去 |

**⚠️ 权衡**：写回仓库需要再放一个 GitHub PAT 到 FC 环境变量里 —— **凭据面又扩大了**。
这是我不把 FC 列为首选的一个重要原因。

## 三、与 GitHub Actions 的对比（决策表）

| 维度 | GitHub Actions（首选） | 阿里云 FC（备选） |
|:---|:---|:---|
| 配置成本 | **零**（已配好） | 中（要建函数、配触发器、传代码） |
| 费用 | 公开仓库**免费不限量** | 有免费额度，超出按调用计费 |
| 结果回写 | **自动 commit 回仓库** | 要额外配（OSS / API / PAT） |
| 凭据暴露面 | 仅 GitHub 自身 | 多一套阿里云 AK + 可能的 GitHub PAT |
| 国内连通性 | 一般 | **好** |
| 内网访问 mackorn.cn | 不能 | **能** |
| 运维负担 | 无 | 要管函数版本、依赖、超时 |

## 四、我的建议（如实说明取舍）

```
第一步：用 GitHub Actions（已经配好，只差你的 3 步操作）
第二步：观察 1-2 周，看 GitHub 连通性是否稳定、结果是否够用
第三步：只有在确实遇到问题时，才上 FC
        —— 因为 FC 会扩大凭据面（多一套 AK），而凭据管理本身就是风险源
```

**我不建议为了"看起来更专业"就上 FC。** 现阶段 FC 的收益（国内连通性）小于成本（多一套凭据 + 运维）。

## 五、如果决定上 FC：具体步骤（供参考，我不代执行）

```
① 登录阿里云控制台 → 函数计算 FC → 创建服务
② 创建函数：
    运行时 Node.js 20
     函数入口 index.handler
     超时 300 秒
     内存 512 MB
③ 代码包内容：
     plugin/  tools/  distribution/07_库/  distribution/03_验证与基准/
     （注意：distribution 里体积较大，建议只带必要的库与基准）
④ 改写入口，把 tools/self_iterate.mjs 的核心逻辑包成 handler：
     exports.handler = async (event, context) => {
       // 依次跑 enforce_lessons / self_iterate
       // 结果 JSON 返回，或写 OSS
     };
⑤ 配置定时触发器（cron 表达式见 2.2）
⑥ 配置环境变量（如需回写：GitHub PAT 或 OSS AK）—— ⚠️ 这是新增凭据面
⑦ 观察日志，确认第一轮跑通
```

**第 ⑥ 步的凭据建议**：用 RAM 子账号 + 最小权限（只给目标 OSS Bucket 的写权限），不要用主账号 AK。
