## 四、三条约定的工作纪律（这轮又加了 4 条）

**原有 3 条**：
```
① 文本替换前先数锚点出现次数，替换后 node --check
② 判据不能有循环依赖（症状：单独跑绿、进门禁红）
③ 判据必须在【真实工具输出】上验证，不是手写 payload
```

**本轮新增 4 条**（都有真实事故）：
```
④ 空 catch {} 是假通过的温床 —— 必须区分"被测对象返回非零"与"根本没跑起来"
⑤ 负控测试要断言【双向】：该保留的保留 + 该改的改了
   （只断言一边，会在"什么都没发生"时假通过）
⑥ 批量改写工具必须排除【测试夹具目录】—— 否则它会改掉自己的负控样本
⑦ "同一行同时含旧值与新值" = 映射表/对比表，不是过时陈述
```

**第 8 条（本轮最有价值的一条思维方法）**：
```
⑧ 事后用正则测某行返回 true 却仍被改 → 说明代码路径与你的理解不符。
   此时【别推理，用负控把它逼出来】。
   （本轮就是靠负控连续揪出 4 个自身 bug，纯推理一个都没找到）
```
